## 4. The bug paragraph

The mechanism is right. The numbers "3" and "156" are not.

Before `ddcaf857` (October 8), `scoreRows` called `jev` once with every candidate in `rows`. `jev` splits questions into batches of 60 (`lib/ai/jev.ts` lines 40-41) and puts the whole state in every batch (lines 45-48). The guard refuses first. `jevBound` throws `state_too_large` when `JSON.stringify(state).length / 2 > 32_000` (`lib/guards/ledger.ts` lines 203-204). That runs before any request (`lib/ai/jev.ts` line 38). A second check adds one question's JSON and uses the same 32,000 line (jev.ts lines 59-64). A third refuses a body over 64,000 estimated tokens (line 66).

The shaped 150-row candidate list is 84,010 characters, which the guard counts as 42,005 tokens. That is the state that exceeds 32,000, before the beat and the posts are added. "About 41,000" is the right neighborhood. "156" is not in the code or the commit. A real run is 150 plus however many quoted accounts survived. The table alone is enough to die. The product commit that contains the guard is `ec162ba2`, September 28, 2026. The September 27 lab figure in `cogs.md` is the run that got through.

Nothing is sent. The guard throws before `fetch`. For 150 questions the old batching would have been 3 requests of 60, each carrying all 150 rows, had the guard allowed it.

After the fix, `scoreRows` splits by the running estimate and keeps each chunk, plus the shared context, at or under 24,000 (`lib/onboarding/engine.ts` lines 329-354). The chunks run together, and one score map is saved once (line 518). The question and the 0.35 line are unchanged. "3 requests" is not the result for the real table. With a short beat and bio, the 150 rows split into 2 chunks, of 89 and 61. Each chunk is still over 60 questions, so `jev.ts` makes 2 requests per chunk. That is 4 requests. Each of those still carries the whole chunk, not only its 60 questions. A long beat and 10 long posts can push this to 3 chunks and 5 requests. The shared context is what moves the count.

Replacement for the request sentence: "Before the fix, one scoring call put all of the candidates in the state. The 150-row list estimates 42,005 tokens, over the 32,000 guard, so the call was refused before it was sent. The 60-question splitter would have made 3 requests, and each would have carried every candidate. After the fix the candidates are split so that each chunk, including the shared beat, bio, and posts, stays under 24,000 estimated tokens. For the 150-row table and a short beat that is 2 chunks, and the 60-question splitter turns them into 4 requests. A long beat and long posts can make it 5. The scores are merged and saved once."
